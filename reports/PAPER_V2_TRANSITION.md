# Переход PAPER Research на `prospective-baseline-v2`

Это отдельная проспективная серия с прежней стратегией `technical-v1`. Переход не меняет и не мигрирует конфигурацию, наблюдения и результаты `prospective-baseline-v1`. Не следует использовать старый ID с новым кодом: его сохранённый source hash должен остаться неизменным, а проверка запуска отклонит несовпадение.

Новая серия регистрируется при первом запуске API Research scanner с `PAPER_EXPERIMENT_ID=prospective-baseline-v2`. В `research_experiments.config_json` фиксируются общий `code_sha256`, отдельные SHA256 пяти исходников стратегии (`strategy_engine.py`, `technical_indicators.py`, `ai_facts.py`, `position_manager.py`, `entry_prefilter.py`) и двух исходников публичного транспорта (`binance_http.py`, `market_data.py`). Сканер сравнивает текущую конфигурацию с сохранённой при запуске и перед каждой записью. Журнал в одной транзакции проверяет сохранённый манифест, начало серии и принадлежность свечи. При несовпадении хешей или конфликте наблюдения запись прекращается; старые строки не заменяются.

Первое наблюдение v2 допустимо только для свечи с временем закрытия **после** `started_at` новой серии. Если та же свеча уже принадлежит другому эксперименту или ранее записана вручную, v2 останавливается с диагностикой `V2_OBSERVATION_OWNER_CONFLICT` или `V2_CANDLE_ALREADY_OBSERVED`. Для общего журнала используются существующие таблицы, без изменения схемы. Повтор той же неизменной записи v2 остаётся идемпотентным.

При плановом переключении задайте одинаковые `PAPER_EXPERIMENT_ID=prospective-baseline-v2` и `PAPER_JOURNAL_PATH` в конфигурациях **API** и **Telegram** в PyCharm. Сканер запускается только в API; Telegram bridge читает тот же журнал и выбирает наблюдения по ID эксперимента. Если автоматические PAPER-входы уже были нужны, их действующие настройки `PAPER_SCANNER_AUTO_PAPER_ENTRIES` и `PAPER_SCANNER_CHAT_ID` должны оставаться согласованными с существующей документацией. Не запускайте два scanner одновременно. Настройки запущенных процессов и `.env` этим изменением не меняются; переход произойдёт только после отдельного планового перезапуска.

Публичный Binance-клиент использует только разрешённые HTTPS GET, не принимает вызывающий `session` и создаёт новую `requests.Session()` с `trust_env=False` для каждого запроса. Поэтому он не читает `.netrc`, proxy и CA-переменные окружения. В среде с обязательным HTTP proxy или корпоративным CA публичные запросы могут перестать работать; настройки сети нужно оценить отдельно, сохраняя анонимный и контролируемый транспорт. Глобальных изменений сетевых библиотек нет. Защита охватывает существующие Binance-вызовы этого приложения, но не сторонний код, который самостоятельно создаёт новый HTTP-клиент.
